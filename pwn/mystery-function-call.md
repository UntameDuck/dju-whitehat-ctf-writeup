# Mystery Function Call

## 결론부터 보기

64바이트 스택 버퍼 뒤에 있는 함수 포인터를 `win()`의 고정 주소 `0x401290`으로 덮었습니다. 함수 포인터는 함수가 반환되기 전에 호출되므로 스택 카나리를 건드리지 않고 제어 흐름을 탈취할 수 있습니다.

## 보호 기법과 공격 표면

- Architecture: amd64
- PIE: disabled
- Canary: enabled
- Stack: executable
- RELRO: disabled
- Symbols: not stripped

카나리가 있다는 사실만 보면 단순 ret overwrite가 어려워 보입니다. 그러나 실제 목표는 반환 주소가 아니라 지역 함수 포인터입니다. 따라서 보호 기법을 나열하는 데서 멈추지 않고, **어떤 시점에 검사가 수행되는지**를 확인하는 것이 중요했습니다.

## 스택 레이아웃

지역 버퍼 `v5`는 `_OWORD v5[4]`, 즉 `16 × 4 = 64`바이트입니다.

```text
v5: [rbp-0x58]  64-byte input buffer
v6: [rbp-0x18]  function pointer
```

두 주소의 차이는 정확히 `0x40`입니다. 길이 검사를 하지 않는 `gets(v5)` 때문에 64바이트 이후의 입력이 `v6`를 덮습니다.

## 표적 함수 선택

호출부는 `v6`에 문자열 포인터를 전달합니다. 따라서 `system@plt`로 덮으면 의도하지 않은 문자열을 명령으로 실행해 실패합니다. 전달된 인자를 무시해도 되는 `win()`이 적절한 표적입니다. PIE가 꺼져 있으므로 심볼 주소 `0x401290`은 원격에서도 고정됩니다.

## 페이로드

```text
64-byte padding || p64(0x401290)
```

재현 스크립트는 [`../scripts/mystery-function-call.py`](../scripts/mystery-function-call.py)에 있습니다.

## 왜 카나리가 막지 못했는가

오버플로우 뒤 프로그램은 `if (v6)` 분기에서 즉시 함수 포인터를 호출합니다. 함수 에필로그의 카나리 검증과 `ret`에 도달하기 전에 제어 흐름이 이미 `win()`으로 이동합니다. 이는 보호 기법의 존재 여부만큼 보호 기법이 적용되는 경로를 이해해야 한다는 좋은 예입니다.

원문에는 최종 플래그 값이 기록되어 있지 않습니다.
