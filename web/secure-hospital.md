# 시큐어 병원

## 취약점 개요

환자 기록은 UUID로 식별되지만, 기록 목록 API가 현재 사용자에게 허용되지 않은 레코드의 UUID와 소유자까지 노출했습니다. 또한 상세 조회 엔드포인트가 요청자와 레코드 소유자의 관계를 다시 검증하지 않아 IDOR/BOLA가 발생했습니다.

## 분석 과정

1. 정상 로그인 후 화면에는 본인(Jane Doe)의 기록만 표시되는 것을 확인했습니다.
2. 개발자 도구의 Network 탭에서 `/api/my_records` 응답을 직접 조사했습니다.
3. UI와 달리 응답에는 여러 사용자 기록의 `owner`와 `id`가 포함되어 있었습니다.
4. `owner`가 `ceo_admin`인 레코드의 UUID를 식별했습니다.

```text
070c9d08-88d7-4804-99d8-1a7790217073
```

5. 상세 조회 URL에 UUID를 직접 대입했습니다.

```text
http://dju-ctf.com:8008/record?record_id=070c9d08-88d7-4804-99d8-1a7790217073
```

CEO의 진료 기록이 열렸고 그 안에서 플래그를 획득했습니다. 원문에는 플래그 값이 기록되어 있지 않습니다.

## 근본 원인

UUID는 추측하기 어렵게 만들 뿐 권한 검사를 대신하지 않습니다. 목록 API의 과도한 데이터 노출과 상세 API의 객체 단위 인가 부재가 결합됐습니다.

## 대응

- 서버에서 `record.owner == authenticated_user`를 매 요청마다 검증합니다.
- 목록 응답에는 사용자가 실제로 열람할 수 있는 레코드만 포함합니다.
- UUID를 비밀값으로 간주하지 않습니다.
- 의료정보 같은 민감 객체에는 접근 로그와 비정상 조회 탐지를 적용합니다.
